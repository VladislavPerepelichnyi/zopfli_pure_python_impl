# Porting notes: util, symbols, hash, cache, lz77

Modules: `zopfli_pure/util.py`, `symbols.py`, `hash.py`, `cache.py`, `lz77.py`.
Reference: `util.h`/`util.c`/`zopfli.h`, `symbols.h`, `hash.c`, `cache.c`, `lz77.c`
with ZOPFLI_LONGEST_MATCH_CACHE, ZOPFLI_HASH_SAME, ZOPFLI_HASH_SAME_HASH,
ZOPFLI_SHORTCUT_LONG_REPETITIONS (used in squeeze.c only) and ZOPFLI_LAZY_MATCHING on.

## Interfaces

As in `docs/PORTING_SPEC.md`. Additions (not replacements):

* `util.init_options(options)` (ZopfliInitOptions).
* `symbols.DIST_SYMBOL`, `DIST_EXTRA_BITS`, `DIST_EXTRA_BITS_VALUE`: tables indexed
  by distance 0..32768. `get_dist_symbol` uses the table.
* `hash.alloc_hash`, `hash.clean_hash`, `hash.update_hash_value`;
  `cache.init_cache`, `cache.clean_cache`; `lz77.init_lz77_store`,
  `clean_lz77_store`, `clean_block_state`, `ceil_div`, `get_length_score`,
  `lz77_get_histogram_at`.
* `LZ77Store.size` is a read-only property (`len(self.litlens)`), so it can never
  get out of sync. squeeze.c re-initializes a store with `ZopfliInitLZ77Store`;
  use `init_lz77_store(data, store)` or a new `LZ77Store(data)`.
* `Hash(window_size)` allocates and resets (C always resets before use).
  `reset_hash` rebuilds the lists (a fresh `[-1] * 65536` etc. is as cheap as an
  in-place reset).

## Types and wrap-around

* `prev`/`prev2`/`same` are `unsigned short` in C. Stored values are window
  indices (< 32768) or `amount`, which `ZopfliUpdateHash` caps at 65535 before the
  store, so no truncation is reachable. `head`/`hashval` hold -1 or < 32768.
* `val2 = ((same - 3) & 255) ^ val`: `same` is promoted to `int`; Python's `&`
  on negative ints matches two's complement.
* `(pos - 1) & ZOPFLI_WINDOW_MASK` at `pos == 0` is 32767 in both languages.
* `LongestMatchCache.length`/`dist` are lists (values <= 258 / <= 32768), `sublen`
  is a `bytearray` (the C `unsigned char` array; `% 256` stores as in C).
* No size_t wrap is reachable in these modules (see UPSTREAM_FINDINGS #22).

## find_longest_match

* `TryGetFromLongestMatchCache`, `StoreInLongestMatchCache` and `GetMatch` are
  inlined into `find_longest_match` (same conditions, same order). `limit` is a
  local, so the C `*limit = length[lmcpos]` update becomes a local assignment
  that the rest of the function (including the store condition
  `limit == ZOPFLI_MAX_MATCH`) sees, as in C.
* On a cache hit with `length == 0` and a sublen buffer, the C returns
  `sublen[0]` as the distance (stale/uninitialized in C). The port does the same
  with its own buffer. Harmless, see UPSTREAM_FINDINGS #18.
* `GetMatch`: the C loop compares 8 bytes at a time while `scan < end - 8`, then
  byte by byte; its result is "first index in [scan, end) where the bytes differ,
  else end". The port computes the same index: if the next 8 bytes match it
  compares the whole remaining range with one slice comparison, else steps in
  32-byte slices, then finishes byte by byte. (This roughly halves the
  time of full searches on repetitive data.)
* The `same`-based skip is reproduced literally (skip `min(same0, same1)`,
  capped at `limit`, only if `same0 > 2` and the first bytes agree). Since the
  `same` values are exact run lengths, the result equals a plain comparison, but
  the port does not rely on that.
* The switch to the second hash (`hhead != h->head2`) is a boolean; only `hprev`
  changes behaviour after the switch (`hhead`/`hhashval`/`hval` are only used in
  C asserts after that point).
* `sublen[bestlength+1 .. currentlength] = dist` is a slice assignment.
* `dist` never exceeds `pos` (C asserts it), so negative Python indices cannot
  occur.

## Store / histograms

* `store_lit_len_dist`: when `origsize % 288 == 0` (resp. 32) the previous
  chunk's cumulative counts (or zeros) are appended, exactly as the
  `ZOPFLI_APPEND_DATA` loop does; `len(ll_counts) == 288 * ceil(size / 288)`,
  like the C allocation that `ZopfliCopyLZ77Store` copies.
* `copy_lz77_store` replaces the lists of `dest` with copies (dest's old data is
  dropped, like `ZopfliCleanLZ77Store`).
* `lz77_get_histogram` fills the caller's 288/32 lists in place (slice
  assignment, list length unchanged).

## Greedy

`lz77_greedy` keeps the C loop with explicit `i += 1` before every `continue`.
`ZopfliVerifyLenDist` is `verify_len_dist` with Python `assert`s (one slice
comparison); it has no effect on results.

## Verification

`tests/test_lz77.py` (pytest, marker `oracle`; large inputs marked `slow`)
builds `tools/harness/lz77/lz77_harness.c` — a unity build of the reference
`util.c`, `hash.c`, `cache.c`, `lz77.c` with asserts on — into
`tools/build/lz77_harness.so` and drives C and Python in lockstep via ctypes:

* symbols: every distance 0..32768, length 0..258, all length/dist symbols.
* hash: full state (val, val2, head, head2, prev, prev2, hashval, hashval2,
  same) after warmup, periodically during updates, at the end and after reset,
  on 19 inputs incl. a 70000-byte run (`same` cap at 65535).
* cache: `sublen_to_cache` / `cache_to_sublen` / `max_cached_sublen` on random
  monotone sublen arrays with 1..30 distinct distances and lengths 0..258.
* find_longest_match: at every position, the (distance, length) result and the
  whole 259-entry sublen buffer (reused across calls, so stale entries are
  compared too), with and without `lmc`, call plans: limit 258 with sublen (as in
  GetBestLengths), limit 258 without sublen, and random sequences of 1..4 calls
  per position with random limits (3..258, biased to small) and random
  sublen/None (as in FollowPath); two passes over the data (second pass hits
  the cache); `instart` 0, size/3 and 40000 (windowstart > 0). Full hash state
  and the whole lmc (length, dist, sublen bytes) are compared at the end of each
  pass.
* greedy: the whole store (litlens, dists, pos, ll_symbol, d_symbol, ll_counts,
  d_counts) plus hash state and lmc afterwards, `instart` 0 / mid / end.
* histograms and byte ranges on random ranges (both branches: < 864 symbols
  and the cumulative-subtraction branch), checked against C and against a
  direct count; copy/append of stores with chunk boundaries.

Inputs: empty, 1, 2, 3 bytes, `aaa`, `aaaa`, `ababa`, runs of 1000/3000/70000
bytes, periods 3/5/7/300, generated text, ACGT, random bytes, 0/1 bytes, mixed
runs, skewed 0/1 data (98% zeros, hits the 8192 chain limit), the reference
C sources (140 KB, > 64 KiB), 70 KB variants of the above.
A line-trace of the Python modules confirmed every line of
`find_longest_match`, `update_hash` and `lz77_greedy` executes on these inputs
(chain-limit break, hash-2 switch, `same` cap, `limit = cached length` path,
lazy-matching branches).
